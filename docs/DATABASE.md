# FishFolk — Database Design

## 1. Principles

- Store observations as structured records.
- Preserve the original text.
- Distinguish event time from submission time.
- Record source type without assuming verification.
- Minimize personal and location data.
- Use migrations and enable Row Level Security where applicable.
- Never expose private records through client-side filtering alone.

## 2. Initial schema

The exact schema should be implemented through SQL migrations and reviewed against the chosen authentication model.

### `profiles` (only if authentication is included)

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key; references `auth.users.id` |
| `display_name` | `text` | Optional public name |
| `created_at` | `timestamptz` | Server-generated |

Do not collect phone numbers or other personal details unless a clear product requirement exists.

### `observations`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key, generated by database |
| `contributor_id` | `uuid` | Nullable for genuinely anonymous submissions; otherwise references profile/auth user |
| `title` | `text` | Optional short title |
| `original_text` | `text` | Required submitted observation |
| `language_code` | `text` | Initially `en`; preserve for future multilingual support |
| `category` | `text` | Must be one of configured categories |
| `source_type` | `text` | `firsthand` or `secondhand` |
| `observed_at` | `timestamptz` | Nullable; when the event occurred |
| `created_at` | `timestamptz` | Server-generated submission time |
| `area_label` | `text` | Optional approximate area; avoid precise coordinates by default |
| `location_precision` | `text` | For example `none`, `approximate`, or `precise` |
| `consent_to_precise_location` | `boolean` | Default false |
| `visibility` | `text` | For example `community` or `private`; define access semantics before enabling |
| `status` | `text` | For example `active` or `removed`; not a verification status |
| `updated_at` | `timestamptz` | Maintained by application or trigger |

Recommended initial categories: `fishing_conditions`, `gear_equipment`, `marine_life`, `local_knowledge`, `other`.

Use database constraints for allowed enum-like values. Do not rely exclusively on frontend dropdowns.

### Optional `observation_audio`

Create this table only if retained audio is a real MVP requirement.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key |
| `observation_id` | `uuid` | Foreign key to observation |
| `storage_path` | `text` | Storage object path, not a public URL |
| `mime_type` | `text` | Validated MIME type |
| `size_bytes` | `bigint` | Enforce a configured maximum |
| `created_at` | `timestamptz` | Upload time |
| `retention_until` | `timestamptz` | Optional retention policy |

Audio must not be stored by default without a clear retention and access policy. If audio is temporary, process it and delete it according to the documented workflow.

### Optional `answer_sources`

For generated answers, keep the source IDs alongside the response or return them directly from the query layer. A separate table is only needed if answer history must be retained.

## 3. Transcript and translation handling

For the English MVP, `original_text` is the submitted text. If transcription is added, consider storing:
- `transcript_text`: transcription result before user correction.
- `original_text`: user-confirmed text used as the observation.
- `language_code`: source language.

For future translations, use a separate related table or explicit translation records keyed by observation and target language. Never overwrite the source text with a translation.

## 4. Indexes

Add indexes for actual query patterns, likely:
- `created_at`
- `category`
- `source_type`
- `observed_at`
- `contributor_id`
- a PostgreSQL full-text search index for observation text

Validate the search configuration and language stemming behavior before selecting a specific text-search configuration.

## 5. Security and RLS

RLS policy decisions depend on whether the MVP is public, authenticated, or invitation-only. Choose and document the access model before enabling writes.

Minimum expectations:
- Public users can only read records intended to be public/community-visible.
- Only authorized users can create records.
- Contributors can edit or remove only records they own, unless a documented moderator role allows more.
- Private records cannot be accessed by unauthorized users.
- Storage access follows the same ownership and visibility model.
- No service-role key is ever exposed to the browser.

Do not ship permissive `USING (true)` write policies as a shortcut.

## 6. Data quality

- `observed_at` may be null.
- Missing locations remain null.
- `source_type` does not imply verification.
- Do not add a `confidence_score` until a defined, tested calculation exists.
- Do not claim a report is verified unless a verification workflow exists.
- Store timestamps in UTC and display them in the user's local time where appropriate.

## 7. Migrations and seed data

- Keep schema changes in version-controlled SQL migrations.
- Seed only clearly labelled demo records.
- Never include real contributor data in committed seed files.
- Test migrations against a clean database and the target Supabase project.
